# Product Direction Shared Contracts v1

Recorded 2026-10-12. Implements the additive shared-contract portion of source execution plan Phase 1 using [accepted decisions](decisions.md). It does not activate a new runtime path or migrate persisted households. `src/constants/schema.js` retains the legacy schemas and exports; distinct v1 schemas add `schema_version: 1`. `src/utils/productDirectionContracts.js` contains pure validators and write-intent builders. Its exceptions expose a stable `error.code` for caller handling.

## Storage and authority

| Record | Identity | Contract and intended authority |
| --- | --- | --- |
| `weeklyPlanDrafts` | Existing `${parent_id}_${student_id}_${week_key}` plan id | Parent-private working copy. `status: draft`, positive `revision`, nonnegative `base_published_revision`. Parent notes and other private review data stay here. |
| `studentDefaultWeeks` | `${parent_id}_${student_id}` | Parent-private, exactly one student. Positive revision; `default_block_quantities` is a subject-id map of curriculum-block-id maps of nonnegative integer quantities. Saving does not write subjects, published plans, or another student's defaults. |
| `weeklyPlans` | Existing plan id | Published/archived portal, report, timer, and extension authority. New v1 snapshots use positive published revision. Public projection contains only approved plan/block/resource/custom-field fields. |
| `blockCompletionStates` | Encoded `block-state:<planId>:<blockId>` | Server-owned effective status projection, revision, immutable original-evidence references, and last correction link. Initial revision is 0; accepted changes increment it. |
| `parentCorrectionEvents` | Encoded `correction:<parentId>:<idempotencyKey>` | Append-only server-written audit. Idempotency keys are unique across that parent's correction requests, including different weeks/students. |
| `weeklyReportAmendments` | Encoded `report-amendment:<originalReportId>:<version>` | Parent-scoped server-written version snapshots. Original saved `weeklyReports` remain unchanged. |
| `routineDaySnapshots` | Encoded `routine-day:<parentId>:<studentId>:<date>` | Server captures qualifying populated templates, stable checklist identities/labels, household timezone, daily reward amount, and enabled setting on first use. Immutable for that local day. |
| `studentCosmeticStates` | Encoded `cosmetics:<parentId>:<studentId>` | Server-owned built-in ownership and persisted slot selections. Positive revision; historical unlock ids remain owned even if absent from the current catalog. |

Encoded ids escape each component independently, so separator characters cannot alias two component tuples. Existing underscore plan/default ids retain their established convention; callers must check stored owner/student identity and actual student ownership rather than treating the id alone as authorization. New id builders reject empty identities. Plan week and routine date keys must be real `YYYY-MM-DD` calendar dates.

The intended direct-read/write boundaries must be enforced in Firestore rules and trusted adapters before activation. Parent-private collections must never be exposed to the public portal or extension. Correction events, effective states, amendments, routine snapshots, and cosmetic ownership must deny direct client writes. Student access receives a validated, student-scoped projection through its trusted boundary. Helpers do not authenticate requests, read Firestore, check entitlements/PINs, perform transactions, or infer server time. Existing public submission creates and parent-controlled weekly-plan writes are still compatibility paths; these helpers alone do not harden them. Their evidence must be resolved and scoped by the adapter before it becomes trusted effective state.

`RoutineRewardCapabilitySchema` represents `daily_routines`, `routine_day_rewards`, and `built_in_cosmetics` separately from broad custom rewards. All three are included in the accepted Free loop. Resolve capabilities through trusted entitlement authority; visibility alone never grants mutation permission. This file does not redefine plan resolution, feature flags, support overrides, or quota policy.

## Publication and revision checks

`buildWeeklyPlanPublishWrites` produces exactly two write intents: updated private draft and public published snapshot. The trusted adapter must read the draft and current published record in one transaction, validate authenticated parent/student ownership, and compare both expected revisions. The supplied draft must be the validated current candidate. Draft revision increments on successful publication, its base becomes the new published revision, and the public revision increments independently. First publication expects published revision 0. A stale draft base, stale draft revision, or stale published revision fails before any write intent is returned. Publication rejects archived targets.

The returned writes must commit atomically. Saving/editing drafts separately must similarly compare their revisions; do not use these objects as permission to overwrite a concurrent edit. `nextContractRevision` rejects malformed, stale, and overflowing revision values. `buildStudentDefaultWeekWrite` scopes both the prior record and replacement to the requested parent/student and only emits a default-record intent.

The public snapshot is allowlisted at every currently modeled nested boundary. Root `parent_notes`/review data, extra block fields, and extra resource/custom-field fields are omitted. Typed public fields reject nested objects disguised as strings. Public `weekly_exceptions` currently accepts text strings; object exceptions fail with `unsupported-weekly-exception` because no structured exception schema is defined or used by the existing seed/runtime examples. Adopt an explicit public shape before publishing structured exceptions; never copy arbitrary private objects into public plans.

## Stable block identity and migration

New block instances need both a stable `id` and immutable `instance_key`, scoped by assignment. `buildStableWeeklyBlockId` accepts an assignment id plus an opaque instance key allocated once for that copy. Repeated copies receive separate keys even when their curriculum definition/title is identical. Never derive new identities from render position, source array order, current quantity, or the current occurrence ordinal. Reordering and republishing preserve ids. Curriculum metadata, legacy indices, and occurrence numbers are compatibility/display references, not identities.

`validateWeeklyBlockInstances` rejects duplicate ids, duplicate assignment/instance pairs, cross-student blocks, unsupported category/completion mode, and invalid completion requirements. `assertRetainedBlockIdentities` rejects id reuse for a different assignment/instance/curriculum definition and a new id for an existing instance. Deletion does not delete its evidence, effective state, audit, or report versions. Later publish adapters must retain historical references and apply any active-timer/completed-work edit policy before accepting removal; the helper does not invent that policy.

For an existing persisted plan, `adoptLegacyWeeklyBlockInstances` retains each exact block id and fills a missing instance key with `legacy:<existing-id>`. Repeating adoption is stable. Missing/duplicate persisted ids require review; do not generate new ids from current subject quantities. Never regenerate completed block identities while adopting a changed subject library.

Legacy evidence mapping is `(student, week, subject, block_index)`. `resolveLegacyWeeklyBlock` checks the student/week before lookup and returns `matched`, `missing`, or `ambiguous`, with all candidate ids. It never picks the first ambiguous record. The trusted evidence adapter must also verify the household and source record, preserve source ids, and quarantine missing/ambiguous mappings for parent review. The old compatibility lookup in `weeklyPlanUtils.js` remains unchanged in this slice and must be replaced at new trusted boundaries. Existing v0 plans cannot be published through v1 helpers without explicit adoption and revision initialization.

## Corrections, evidence, and amendments

`buildParentCorrection` accepts a request containing only `new_status`, nonempty `reason`, text `note`, `idempotency_key`, and `expected_revision`. Accepted statuses are `incomplete` and `completed`. Requests cannot supply actor/time, rewrite summaries or answers, replace resources, change an assignment, or rewrite evidence. The trusted adapter supplies authenticated `actorId`, its server clock value, the exact plan/block state, and the original evidence reference records resolved from storage. Parent actor must match plan owner. Helpers check every original evidence reference against parent/student/week/plan/block scope and require exact agreement with the state's evidence ids.

The event records prior/new status, prior/new revision, stable identity, reason/note, actor/time, idempotency, and references to the original evidence. Undo sets effective state to incomplete and retains original submissions. It does not undo archived status. A later trusted valid student submission can complete current work again; that submission path is outside this slice and must retain the old evidence while adding the new evidence reference. Tests cover a later status change without deleting the original reference, not implementation of the student submission path.

The trusted adapter reads idempotency event plus state in the same transaction. A matching replay returns `replayed: true` without a new revision/event. Reusing the key with a different target, payload, or expected prior revision fails. Event writes are create-only; never edit/delete the original audit entry. The helpers preserve the state on replay even if later changes advanced it.

`buildReportAmendment` accepts a root original report, the latest amendment if one exists, applicable scoped correction events, and a trusted recomputed full report snapshot. Original is logical version 1. First amendment is 2 and links to the root id; each subsequent amendment links to both the root and its immediate preceding version. Expected version is checked, and mismatched household/student/week/plan links fail. The adapter must query/transactionally establish the latest version, validate the loaded events, and recompute totals from effective state. The helper cannot prove a supplied snapshot's totals. It does not overwrite the original, mutate archived plans, or put archived work back in the current portal. Legacy `snapshot_model: subjects` root reports retain an empty or missing original plan reference. Their amendments normalize only the amendment link to an empty string, retain the subject snapshot model, and require consistent parent/student/week. The amended report snapshot and amendment chain retain the empty original report plan reference. A genuine correction event may retain its authoritative nonempty plan reference for that same parent/student/week; the helper links its original event id without changing the event or its original evidence references. No invented plan id is added to the original. Weekly-plan-backed reports require a nonempty exact plan link. The trusted legacy correction adapter must resolve stable evidence/block references before providing these subject-scoped events.

## Routine and cosmetic validation

`validateRoutineDaySnapshot` checks the real household-local date, IANA timezone, unique qualifying periods/template ids, nonempty checklists with stable unique item ids, and nonnegative configured points. Empty `templates` is a valid empty-day snapshot but `isRoutineDaySnapshotComplete` returns false, preventing an empty-day award. Completion requires every snapshotted item in every populated period. The trusted award transaction must enforce one award per parent/student/date, use the existing `routine_day:<date_key>` ledger source within the student wallet scope, and derive the first-use date/timezone from household settings. New reward settings default to 10 points; existing valid values remain unchanged. Later template edits never alter today's first-use snapshot.

`validateStudentCosmeticState` checks student scope, revision, unique ownership ids, and selection membership in ownership. Nonempty selections must be active built-in catalog entries for the matching slot. Empty slot selection is allowed. Historical owned ids may remain absent from the new catalog, but cannot be selected without a compatible catalog entry. The trusted adapter derives ownership from existing unlocks and valid grant/redemption transactions, checks server-approved catalog ids/costs, and saves selection with a revision check. Validation does not itself grant unlocks, spend points, or permit broad custom rewards.
